#### What an upgrade asks of your crate

Two hundred and twenty-nine rules meet a crate that upgrades. Each is stated with what a build or a read answers:



- **A model type is emitted as `{Name}Draft`, and `{Name}` is the valid type**, so every struct literal, tuple constructor and variant path of a model type stops the build: `Shipment { label, parcel_count: 3 }` is ``error[E0560]: struct `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>` has no field named `label` ``, `Pair(1, 2)` is ``error[E0423]: cannot find function, tuple struct or tuple variant `Pair` in this scope`` with ``a type alias named `Pair` exists in another namespace``, and `Payment::Card { .. }` is ``error[E0223]: ambiguous associated type`` or ``error[E0599]: no associated function or constant named `Cash` found for struct `__tixschema_valid_payment_schema::Payment<PaymentDraft>` in the current scope``. The idea is to work with the valid type as much as possible: a field, a parameter, a return type, a constant and an impl name `Shipment`, and a draft appears only on the expression that builds or changes a value. Write `ShipmentDraft { label, parcel_count: 3 }.validate()?`, `PairDraft(1, 2).validate()?` and `PaymentDraft::Card { .. }.validate()?` there. Where nothing can fail, write the constant `Payment::Cash` (a unit variant, see the rule on constants below) or `.into()` (a draft that declares no rule, see the rule on `From` below), and never `.validate().unwrap()` outside a test. A `match` over a value that must stay valid is `match &*payment { PaymentDraft::Card { .. } => .. }`; a destructuring `let Shipment { label, .. } = shipment;` is `let ShipmentDraft { label, .. } = shipment.into();`. Every surface other than Rust (TypeScript, Zod, JSON Schema, Dart, Swift, Kotlin, MCP and OpenAPI) keeps the declared name. A brand has no draft. See [A Draft and a Valid Type](models.md#a-draft-and-a-valid-type).
- **`validate` takes the draft and answers the valid value**: `validate` is a method of `{Name}Draft` that consumes it, so `shipment.validate()` on a value of the valid type stops the build with ``error[E0507]: cannot move out of dereference of `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>` ``, and `assert_eq!(draft.validate(), Ok(()))` with ``error[E0369]: binary operation `==` cannot be applied to type `Result<__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>, Vec<String>>` ``. Write `let shipment = draft.validate()?;`, which returns the valid value and every message `validate()` gave, in the same order and the same words. A struct a service writes for itself, such as a generated message, keeps `validate(&self)`.
- **The violations of a draft are `validation_issues()`**, which borrows the draft and answers `Vec<String>`: `draft.validate().unwrap_err()` consumed the value it checked, so `.validate().is_ok()` and `.validate().is_err()` on a draft you still use stop the build with ``error[E0382]: borrow of moved value: `draft` `` at the next use of the draft. Write `draft.validation_issues().is_empty()`, `!draft.validation_issues().is_empty()` and `draft.validation_issues()`. The valid type has `validation_issues()` too, which lists what its draft lists.
- **A function a `check` names takes `&{Name}Draft`**, the type the rules run on: `fn ends_after_start(window: &Window) -> Result<(), Vec<String>>` stops the build with ``error[E0308]: mismatched types`` and ``expected `&Window<WindowDraft>`, found `&WindowDraft` ``. Write `fn ends_after_start(window: &WindowDraft) -> Result<(), Vec<String>>`, and read a member as `window.start`.
- **A member of a valid value is read and not changed or moved**: `shipment.parcel_count = 1` stops the build with ``error[E0594]: cannot assign to data in dereference of `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>` ``, `&mut shipment.parcel_count` with ``error[E0596]``, and `shipment.label` moved out of a valid value with ``error[E0507]: cannot move out of dereference``. Turn the value into its draft with `let mut draft: ShipmentDraft = shipment.into();`, change it, and call `validate()` again; clone a member you only read, or move it out of the draft.
- **`#[derive(Default)]` stays on the draft and is not written on the valid type**: `Shipment::default()` and a member `#[serde(default)]` of a model type stop the build with ``error[E0599]: no associated function or constant named `default` found for struct `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>` in the current scope`` or ``error[E0277]: the trait bound `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>: Default` is not satisfied``, because a default would build a valid value with no check. `Default` stays on the draft: a hand-written `impl Default for Shipment` is `impl Default for ShipmentDraft`. A default valid value comes from `ShipmentDraft::default().validate()?`, or from `ShipmentDraft::default().into()` where the type declares no rule, and `#[serde(default = "path")]` on a member typed with a model type names a function that answers the valid type, `fn default_shipment() -> Shipment { ShipmentDraft::default().into() }`.
- **A model type's `Deserialize`, a MongoDB read and a dispatcher's read answer the valid type**, with the messages they answered before: `serde_json::from_str::<Shipment>(text)` refuses a value that breaks a rule with the text `validate()` gave, `Shipment::model_schema_read_unjudged` reads with no check for a holder, and `ShipmentDraft` reads as serde reads it, with no check. Name the draft where a read should not refuse.
- **A hand-written impl on a model type stays on the valid type, and reads through `Deref`**: `impl Shipment { fn label_text(&self) -> String { .. } }` builds and reads the members as before. An impl matches the variants of an enum through the constants (`matches!(*self, Payment::Cash)`, or `match *self { Payment::Cash => .., Payment::Check => .. }` with `PartialEq` and `Eq` derived, since a constant pattern needs structural equality) or through `match &**self { PaymentDraft::Card { .. } => .., .. }`, and it answers a model value as the valid type: the constant, or `.into()`, where nothing can fail, and `.validate()?` where a rule can. An impl that builds the value with `Self { .. }` or `Self::Card { .. }` stops the build with ``error[E0560]``, or ``error[E0223]: ambiguous associated type`` for `Self::Card { .. }`: build the draft on that expression and validate it there. Only an impl that must change a value in place goes on `impl ShipmentDraft`, which is the type with the members and the variants.
- **`#[model_schema]` goes above the `#[derive]` of the item**: a `#[derive(Debug)]` written above it is applied by the compiler to the item as written, which the macro rewrites, so `#[derive(Debug, Serialize, Deserialize)] #[model_schema()] pub struct Order { pub id: String }` stops the build with ``error[E0560]: struct `__tixschema_valid_order_schema::Order<OrderDraft>` has no field named `id` ``. Write `#[model_schema()]` first and the derives below it.
- **A module that expands a dispatcher or an MCP interview names the draft of an error it maps**: `error_status(NotFound = 404)` and an elicitation arm match on `{Error}Draft`, so a module that imports `FolderError` for `folder_service_http_rest_dispatcher!()` stops the build with ``error[E0433]: cannot find type `FolderErrorDraft` in this scope``. Import `FolderErrorDraft` beside it. The error type is a `#[model_schema()]` type: a plain `#[derive(Serialize, Deserialize)]` enum under `error_status` answers ``error[E0614]: type `GetVersionError` cannot be dereferenced`` and the same ``E0433``.
- **`unwrap_err()` and `unwrap()` on `validate()` ask the model for `Debug`**: `RegistrationDataDraft { .. }.validate().unwrap_err()` over a type that derives no `Debug` stops the build with ``error[E0277]: `__tixschema_valid_registration_data_schema::RegistrationData<RegistrationDataDraft>` doesn't implement `Debug` ``, where `validate()` answered `Result<(), Vec<String>>`. Derive `Debug` on the model, or write `.validate().err().unwrap()`.
- **A `Serialize` or `Deserialize` written by hand is written for the draft**: a model that derives neither has them on the valid type only where it derives them, so reading a `Measurement` whose `Deserialize` is `impl<'de> Deserialize<'de> for MeasurementDraft` stops the build with ``error[E0277]: the trait bound `__tixschema_valid_measurement_schema::Measurement<MeasurementDraft>: serde::Deserialize<'de>` is not satisfied``. Read `MeasurementDraft`, or derive `Deserialize` on the model.
- **A hand-written `validate(&self)` of a message that is no model is no longer called**: a struct that only derives `Serialize` and `Deserialize`, beside the service it is a message of, and that declares `fn validate(&self) -> Result<(), Vec<String>>`, builds with ``warning: method `validate` is never used`` where the method is private (a `pub` one draws no warning), and a dispatcher and a client let a broken message through. Write `pub fn validation_issues(&self) -> Vec<String>`, the report as a list that is empty where the message passes.
- **A `validate(&self)` the author wrote on a model type is the author's own**: `impl Loose { pub fn validate(&self) -> Result<(), Vec<String>> { .. } }` builds beside the macro's, and a holder of a `Loose` does not call it, so a rule it states reports nothing. Move the rule into a `check` the model names.
- **`validate()` calls are not `const`**: `const fn reading(size: i64) -> ScaleReading { ScaleReadingDraft { size, weight: 2.0 }.validate().unwrap() }` stops the build with ``error[E0015]: cannot call non-const method `ScaleReadingDraft::validate` in constant functions``. Make the function a plain `fn`, and a `static` that holds a valid value a `LazyLock`.
- **A unit struct's value is its constant on the valid type**: `Ok(SealAck)` and `serde_json::to_string(&SealAck)` build, where the unit struct is `#[model_schema()] pub struct SealAck;` and declares no rule, and the value is the valid one. A unit struct that names a `check` has no constant: its value is `SealAckDraft.validate()?`. The constant is named like the struct, which is not an upper case name, so the macro writes `#[expect(non_upper_case_globals, reason = "..")]` on it; a crate that denies warnings builds with it.
- **A value a MongoDB path takes is a valid one**: `paths.status().eq(InvoiceStatus::PastDue)` over a plain enum takes the variant, and a value that is not a unit variant is made on the expression that builds it, with `.validate()?`.
- **A unit variant of an enum with a draft, and a unit struct, are constants of the valid type**: `Payment::Pending` is a `Payment` in an expression (`let state: Payment = Payment::Pending;`, `fn default_state() -> Payment { Payment::Pending }`) and in a pattern, where the enum derives `PartialEq` and `Eq` (`match state { Payment::Pending => 1, Payment::Card(_) => 2 }`; rustc counts the constants toward exhaustiveness, so a match over the unit variants and the others needs no `_` arm). Without `PartialEq` and `Eq` a match on a constant stops the build with ``error: constant of non-structural type .. in a pattern``, and the constant works in an expression. An enum with data-carrying variants has a constant for each unit variant alone, and an enum that names a `check` has none, since a check could refuse a unit variant: write `PaymentDraft::Pending.validate()?`. Each constant is named like its variant, which is no upper case name, so the macro writes one `#[expect(non_upper_case_globals, reason = "..")]` on the `impl` that holds them, and none for an enum whose unit variants are all upper case. A generic enum has no constant. TypeScript has `Payment.Pending` (the value the enum's tagging writes for a variant with data), Dart `Payment.pending`, Swift `Payment.pending` and Kotlin `Payment.Pending`, each a value of the valid type, and a unit struct that declares no rule has `SealAck` (TypeScript), `SealAck.instance` (Dart, Swift and Kotlin). An enum whose variants are all unit variants and that names no `check` has no draft, and its variants are its values: see the next rule.
- **A plain enum that names no `check` has no draft on any surface**: an enum whose variants are all unit variants, written as their bare names (no `tag`, no `content`, no `untagged`), and that names no `check`, is declared as written, as a brand is. `InvoiceStatusDraft` stops the build with ``error[E0433]: cannot find type `InvoiceStatusDraft` in this scope`` and ``error[E0412]``, `InvoiceStatusDraft::PastDue.validate()?` with the same error, `InvoiceStatus::PastDue.validate()` with ``error[E0599]: no method named `validate` found for enum `InvoiceStatus` ``, `draft.into()` where a draft became a valid value with ``error[E0599]``, and `*status`, `&**status` and `&*status` over the value with ``error[E0614]: type `InvoiceStatus` cannot be dereferenced``. Write `InvoiceStatus::PastDue` where each stood, and `match status { InvoiceStatus::Draft => .., InvoiceStatus::PastDue => .., InvoiceStatus::Paid => .. }` with no `_` arm. The enum keeps `validation_issues(&self)`, which answers an empty list, so a holder's walk calls it as before, and `wire_name`, `enum_members`, `MONGO_FIELDS`, `ts_definition`, `zod_schema` and `json_schema`. In TypeScript `InvoiceStatusDraft$valid` and `toValid` are gone, and `InvoiceStatus` is the string union `"draft" | "past-due" | "paid"` with no `Readonly<>` and no `$brand<"InvoiceStatus">`, which indexes a `Record<InvoiceStatus, number>` and narrows in a `switch`, where the branded type was `error TS7053` as a key and `error TS2366` in a `switch` with no `default`; `InvoiceStatus.PastDue` is the literal `"past-due"`, and `InvoiceStatus$Schema` parses to the union with no `.brand`. A `{Name}Draft` name is written, as an alias of the union, only where a holder declared above the enum named it. Dart, Swift and Kotlin write the enum as their native enum, as before the draft: `InvoiceStatus.pastDue` in Dart and Swift, `InvoiceStatus.PastDue` in Kotlin, with no `InvoiceStatusDraft`, no `toDraft()`, `draft` or `toValid()`. A plain enum that names a `check`, and every other enum, keeps its draft and its valid type. `error_status(..)` of a service, and an MCP elicitation arm, match an error enum of this kind by its own name when it is declared above the service, so import `InvoiceStatus` alone.
- **A draft that declares no rule becomes its valid type with `From`, and with no `Result`**: `let rule: RuleResult = RuleResultDraft { passed: true, label }.into();` builds, where `RuleResult` has no `model_schema_prop` constraint, no `check`, no literal, and is no brand: a member typed with another model type is no rule (`pub role: SessionRole`), and `.into()` does not judge a member written as a draft type, so a field names the valid type. A struct that declares a rule has no `From`: `ShipmentDraft { label }.into()` stops the build with ``error[E0277]: the trait bound `__tixschema_valid_shipment_schema::Shipment<ShipmentDraft>: From<ShipmentDraft>` is not satisfied``, and its value comes from `validate()?`. The other languages convert a draft the same way: TypeScript `ShipmentDraft$valid(draft)`, Dart `draft.toValid()`, Swift `draft.valid` and Kotlin `draft.toValid()`, each on the draft of a type that declares no rule and absent from the others.

- **`Shipment$Schema` parses to the valid type, and the schema of the plain type is `ShipmentDraft$Schema`**: code that parsed to a `ShipmentDraft`-shaped value and then built or changed it names `ShipmentDraft$Schema`.
